# Трекер обращений

Личный журнал обращений и отвлечений. Репозиторий содержит веб-интерфейс, Cloudflare Worker API, миграции D1 и автоматические проверки. Исходные требования находятся в [плане 1.3](docs/product-plan-1.3.md).

> Текущая реализация — начальная версия, не прошедшая полную приёмку по спецификации. Перед использованием для личных данных необходимо проверить перечисленные ниже ограничения и настроить защиту Cloudflare Access для всего приложения.

## Разработка

Требуются Node.js 22.13 или новее, npm и Python 3 для SQL-тестов.

```sh
npm ci
npm run migrate:local
npm test
npm run check
npm run dev
```

Миграции команды `migrate:local` применяются только к локальной D1. `check` проверяет сборку без публикации. API закрывает запросы при отсутствии настроек Access и корректного подписанного JWT; локальный обход авторизации в код не добавлен. Тесты используют тестовые подписи и локальную SQLite, не затрагивая production.

## Подготовка Cloudflare

1. Создайте отдельную D1 и укажите её ID в `wrangler.jsonc`. Применяйте миграции к реальной базе только после проверки её состояния и разрешения владельца.
2. Настройте Cloudflare Access на весь адрес приложения, включая preview и любые дополнительные домены, с политикой для email владельца. Приложение дополнительно проверяет JWT для API.
3. Задайте переменные Worker `ACCESS_TEAM_DOMAIN` (например, `https://example.cloudflareaccess.com`), `ACCESS_AUD` и `ACCESS_EMAIL`. Для LLM задайте секрет `LLM_API_KEY` через `wrangler secret put LLM_API_KEY`; ключ не должен попадать в Git или браузер. Модель и адрес API настраиваются в приложении.
4. До работы с личными данными проверьте отказ незалогиненному пользователю, вход владельца, работу локальной и удалённой D1, резервное копирование и все обязательные сценарии плана. Реальное развёртывание и настройка Access не выполнялись.

Статика обслуживается Worker Assets; `/api/*` направляются в Worker до SPA fallback. Данные и секреты не включены в репозиторий.

## Проверки и ограничения

Тесты используют SQLite и подмену внешних сервисов; они не заменяют проверку реальной D1, Access, двух устройств, iPhone и поведения при плохой сети. `npm run check` не публикует Worker. Сохранение отчёта с одним ID резервирует одну попытку вызова модели; повтор после неизвестного исхода не выполняется автоматически. Экспорт читается страницами и не является атомарной резервной копией D1.

Полная приёмка, обработка всех состояний сети и конфликтов, точность ввода времени для произвольных часовых поясов и сценарии интерфейса из плана требуют дополнительной проверки и доработки. Не считайте эту версию готовой к production до прохождения приёмки.

Известные функциональные пробелы относительно плана 1.3:

- Ручной ввод времени работает только при совпадении часового пояса устройства и настройки; неоднозначное время при смене UTC-смещения отклоняется, выбор смещения не реализован.
- Нет полного пофильного разрешения конфликтов и сохранения всех ручных форм при обрыве связи. Восстановление неизвестного результата реализовано не для всех команд.
- Не реализованы ручное окончание забытого таймера, полная детализация статистики, пагинация и удаление отчётов в интерфейсе, признаки свежести отчёта. Последние источники выбираются из 100 последних записей.
