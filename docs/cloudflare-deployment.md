# Развёртывание и обслуживание на Cloudflare Workers

Инструкция относится к текущему коду репозитория. Она описывает **новую установку** на `workers.dev` через Wrangler. Для обновления существующей установки используйте раздел «Обновление»: не создавайте новую базу и не очищайте параметры Access.

В результате будут один Worker со статическими файлами и API, одна D1 и Access-приложение с доступом по email владельца. Собственный домен и LLM необязательны. VPS, Docker, Cloudflare Tunnel и отдельный веб-сервер не требуются.

## 1. Подготовить инструменты и исходники

Нужны аккаунт Cloudflare с возможностью управлять Workers, D1 и Zero Trust / Access, Node.js 24, npm, Git и Python 3 для SQL-тестов. Подойдут личные аккаунты в пределах доступных тарифов и квот.

```sh
git clone https://github.com/HyperDodo/distractions-tracker.git
cd distractions-tracker
npm ci
npm test
npm run check
npx wrangler login
npx wrangler whoami
```

`login` открывает вход в браузере и разрешение Wrangler на работу с аккаунтом. Это авторизация для управления Cloudflare, не ключ языковой модели и не вход пользователя в приложение. `whoami` позволяет проверить выбранный аккаунт. Если аккаунтов несколько, при необходимости добавьте его `account_id` в конфигурацию ниже.

На этом этапе `npm run check` выполняет только dry run. Приложение не публикуется, удалённая база не создаётся и не изменяется.

## 2. Создать новую D1 и конфигурацию

Для **новой пустой установки**:

```sh
npx wrangler d1 create interruption-tracker
cp wrangler.production.example.jsonc wrangler.production.jsonc
```

Команда создания базы выведет `database_id`. Если Wrangler предлагает автоматически добавить binding в текущую конфигурацию, выберите **No**: ниже настраивается отдельный файл. В локальном `wrangler.production.jsonc` замените `REPLACE_WITH_D1_DATABASE_ID` на этот UUID. Имя базы должно совпадать с созданным. Binding оставьте **`DB`** — его использует код.

Сохраните `name: "interruption-tracker"` либо выберите свободное имя Worker. Дальнейшие команды должны относиться к одному и тому же Worker и аккаунту. Имя Worker и имя базы могут различаться, но не переименовывайте их случайно при обновлении.

Шаблон содержит:

- `main: "backend/worker.js"` — точка входа API;
- `assets.directory: "./frontend/public"` и binding `ASSETS` — интерфейс;
- `assets.run_worker_first: ["/api/*"]` — API обрабатывается до SPA fallback;
- `workers_dev: true` — адрес на `workers.dev`;
- `preview_urls: false` — отключение отдельных Version URLs;
- `vars: {}` — пока без параметров Access, API будет закрыт.

`wrangler.production.jsonc` исключён из Git. Файл должен оставаться в корне репозитория: относительные пути рассчитаны на это расположение. Все команды дальше передают `--config wrangler.production.jsonc` явно. Не путайте этот файл с исходным `wrangler.jsonc`, который содержит заглушку базы и используется командами локальной разработки.

## 3. Применить миграции к новой базе

Сначала посмотреть ожидающие миграции:

```sh
npx wrangler d1 migrations list interruption-tracker --remote --config wrangler.production.jsonc
```

Затем применить их:

```sh
npx wrangler d1 migrations apply interruption-tracker --remote --config wrangler.production.jsonc
```

Это первая команда инструкции, изменяющая схему **удалённой** базы. Wrangler показывает миграции и запрашивает подтверждение при интерактивном запуске. Для новой базы применятся `0001_init.sql` и `0002_reports.sql`; вручную повторять `CREATE TABLE` не нужно.

`--local` означает другую, локальную базу, а не проверку production. Успешное применение миграций с `--local` не заменяет `--remote`. Для существующей базы сначала нужен резервный экспорт и проверка фактической схемы; эта инструкция не выполняет автоматический upgrade произвольной старой установки.

## 4. Первоначально загрузить Worker с закрытым API

Для этой новой установки пока оставьте `vars: {}`. Не вводите личные записи и не добавляйте ключ LLM.

```sh
npx wrangler deploy --config wrangler.production.jsonc --dry-run
npx wrangler deploy --config wrangler.production.jsonc
```

Вторая команда уже публикует Worker. Wrangler выведет адрес вида:

```text
https://interruption-tracker.<your-subdomain>.workers.dev
```

При первом развёртывании Cloudflare может предложить выбрать account subdomain для `workers.dev`. Используйте фактический URL из результата, а не копируйте адрес-пример.

Пока параметры Access отсутствуют, запрос `/api/settings` вернёт `503` с кодом `AUTH_CONFIGURATION_ERROR`: это ожидаемый закрытый режим. Статические HTML/JS/CSS на данном этапе могут быть доступны публично; в них нет пользовательского журнала или ключа. Весь адрес нужно закрыть следующим шагом **до включения API и ввода личных данных**.

## 5. Включить Cloudflare Access для всего приложения

В аккаунте Cloudflare включите Zero Trust и настройте способ входа. Для одного владельца подходит одноразовый код на его email; можно использовать и настроенного поставщика идентификации.

Предпочтительный вариант по документации Cloudflare — защита на уровне Worker:

1. **Workers & Pages → ваш Worker → Access**.
2. Выберите **Protect this Worker behind Access**.
3. Для области защиты выберите **All traffic**, не только previews.
4. Настройте Allow-политику с **точным email владельца**. Не разрешайте всех пользователей или весь почтовый домен вместо одного адреса.
5. Примените политику и проверьте созданное Access-приложение в Zero Trust / Access.

Защита Worker по документации распространяется на связанные с ним домены и preview-адреса. Если интерфейс аккаунта предлагает только защиту по hostname, создайте Self-hosted Access application на **весь фактический hostname без ограничения `/api`**; каждый дополнительный hostname нужно защитить отдельно. `workers.dev`, собственный домен и preview — разные способы попасть к приложению.

`preview_urls: false` управляет Version URLs; новые отдельные preview-окружения также необходимо отключить или защитить. Нельзя считать, что защита одного production-hostname автоматически закрывает все другие адреса.

После настройки найдите три значения:

| Имя | Откуда взять | Важная деталь |
| --- | --- | --- |
| `ACCESS_TEAM_DOMAIN` | Team domain в настройках Zero Trust | Полный адрес `https://your-team.cloudflareaccess.com`, без дополнительных путей. Это не домен Worker |
| `ACCESS_AUD` | Application Audience (AUD) **этого Access-приложения** | Не Account ID и не ID базы D1; не генерируйте его самостоятельно |
| `ACCESS_EMAIL` | Email владельца | Должен совпадать с разрешённым адресом и email в JWT |

В локальном `wrangler.production.jsonc` замените пустой объект `vars`:

```json
"vars": {
  "ACCESS_TEAM_DOMAIN": "https://your-team.cloudflareaccess.com",
  "ACCESS_AUD": "YOUR_ACCESS_APPLICATION_AUD",
  "ACCESS_EMAIL": "owner@example.com"
}
```

Здесь показан фрагмент конфигурации, не отдельный полный JSON-файл. Подставьте реальные значения. Значения AUD и issuer не являются API-ключом; email — личная настройка, поэтому рабочий файл исключён из Git.

После того как Access включён, выполните:

```sh
npx wrangler deploy --config wrangler.production.jsonc
```

Альтернативно эти три значения можно задать как Variables в Dashboard. Тогда последующие деплои нужно выполнять с `--keep-vars` либо `keep_vars: true`: Wrangler по умолчанию заменяет обычные переменные значениями из конфигурации. Рекомендуемый здесь путь — хранить все три в локальном конфигурационном файле; не смешивайте источники без необходимости. Worker Secrets при обычном деплое сохраняются отдельно.

## 6. Проверить защищённый запуск

Прежде чем пользоваться приложением:

1. Откройте основной URL в приватном окне. Должен появиться вход Access или отказ, но не личный журнал. Проверьте также `/api/settings`, `/api/snapshot` и `/api/export?format=json` без входа: они не должны возвращать личные данные.
2. Войдите разрешённым email. Запрос `/api/settings` после входа должен вернуть JSON с HTTP `200`. Используйте вкладку Network инструментов браузера; обычный `curl` не проходит пользовательский вход Access автоматически.
3. Проверьте, что другой email не получает доступ. Обычный `403` означает запрет, а не необходимость бесконечно повторять вход.
4. На компьютере начните обращение. На телефоне войдите тем же email и завершите его; должна остаться одна запись с одним началом и окончанием.
5. Перезагрузите страницу и убедитесь, что завершённая запись осталась. Проверьте ручную запись, исправление, дневную сводку и выгрузку.
6. Проверьте все дополнительные домены, Version URLs и отдельные preview-окружения: они должны быть закрыты или отключены. Проверка только `/` основного адреса недостаточна.

**Это ручная приёмка, а не уже выполненные проверки.** Текущие известные функциональные ограничения перечислены в [README](../README.md#что-проверено-и-что-осталось). Настройка Cloudflare сама по себе их не устраняет.

## 7. Необязательно: подключить разбор LLM

Без этого шага журнал и числовая статистика работают. Для разбора:

1. Создайте API-ключ у OpenRouter или совместимого поставщика. Выберите модель и проверьте её текущую цену и лимиты. Оплата API не связана с подпиской ChatGPT.
2. Сохраните ключ интерактивно:

   ```sh
   npx wrangler secret put LLM_API_KEY --config wrangler.production.jsonc
   ```

   Команда запросит значение без необходимости вставлять его в командную строку. По документации `secret put` создаёт и сразу развёртывает новую версию Worker. Через Dashboard тот же секрет добавляется в **Worker → Settings → Variables and Secrets → Secret**. Не используйте обычную переменную или поле в браузере для ключа.

3. В настройках приложения выберите поставщика, base URL и точный идентификатор модели. Для OpenRouter base URL — `https://openrouter.ai/api/v1`. Для другого поставщика укажите его совместимый адрес **до** `/chat/completions`: приложение добавляет этот путь само.
4. Выбранному base URL отправляется ключ, поэтому используйте только HTTPS-адрес доверенного поставщика. При смене поставщика замените и ключ.
5. Нажмите «Проверить модель» один раз. Проверка тоже обращается к API и может оплачиваться. Потом проверьте разбор непустого дня.

Снимок анализа включает записи и заметки. Ключ остаётся на сервере. Некорректный JSON от модели или потеря ответа не означают, что запрос был бесплатным. При `failed` или `unknown` новый платный запуск требует отдельного явного действия; старый `report_id` не должен запускаться повторно.

## Обновление существующей установки

Рабочий `wrangler.production.jsonc` и его параметры должны сохраниться. Не копируйте шаблон поверх настроенного файла. Используйте прежние Worker, D1 и Access-приложение.

Перед обновлением создайте резервную копию в непубличном месте. Например, из корня репозитория:

```sh
mkdir -p .backups
npx wrangler d1 export interruption-tracker --remote --output .backups/before-update-01.sql --config wrangler.production.jsonc
```

Для каждого экспорта выбирайте новое имя файла. `.backups/` исключён из Git, но резервные копии содержат личные данные и должны храниться защищённо. Скопируйте нужные копии за пределы временной рабочей среды и проверяйте возможность восстановления на отдельной тестовой базе. Экспорт JSON/CSV приложения полезен для просмотра данных, но не заменяет штатное обслуживание D1.

Далее:

```sh
git pull --ff-only origin main
npm ci
npm test
npm run check
npx wrangler d1 migrations list interruption-tracker --remote --config wrangler.production.jsonc
```

Изучите новые миграции. Если они есть и соответствуют фактической схеме, примените их после резервного копирования:

```sh
npx wrangler d1 migrations apply interruption-tracker --remote --config wrangler.production.jsonc
npx wrangler deploy --config wrangler.production.jsonc
npx wrangler deployments list --config wrangler.production.jsonc
```

Не редактируйте уже применённые миграции, не удаляйте базу для обновления и не меняйте `database_id` на новый. Повторное выполнение `migrations apply` применяет только ожидающие миграции. После деплоя проверьте вход, прежнюю историю и активный таймер, а также защиту всех адресов.

При проблеме с новой версией откат Worker доступен в Cloudflare Deployments; он **не откатывает изменения базы**. Совместимость схемы и кода, восстановление D1 и операции Time Travel требуют отдельной проверки. Восстановление не запускается автоматически.

## Собственный домен и автоматический деплой из GitHub

Для личного запуска достаточно `workers.dev`. Если нужен собственный домен, добавьте Worker Custom Domain в Cloudflare, проверьте, что Access закрывает его, и убедитесь, что старые адреса тоже защищены. Если отключаете `workers.dev` в Dashboard, закрепите `workers_dev: false` в рабочем файле конфигурации: иначе следующий деплой может включить его снова. Оставьте `preview_urls: false` и отдельно проверьте preview-окружения. Cloudflare Tunnel для этого Worker не нужен.

Автодеплой необязателен; сначала проверьте ручную публикацию. Для Workers Builds можно подключить GitHub-репозиторий и ветку `main`. В этом варианте:

- Персональный игнорируемый `wrangler.production.jsonc` не появится в CI сам. Подготовьте конфигурацию окружения в CI либо перенесите согласованные **несекретные** значения в отслеживаемый Wrangler config.
- Выберите корень репозитория и команду публикации, указывающую существующий конфигурационный файл. Установку зависимостей выполняйте по lockfile, используйте Node.js 24 и запускайте тесты до публикации. Python-тесты требуют Python и в CI.
- Секрет выполнения Worker `LLM_API_KEY` хранится как runtime Secret Worker. Build variables/credentials для CI — отдельные настройки, они не становятся `env.LLM_API_KEY` автоматически.
- Проверку и применение миграций D1 предусмотрите отдельным контролируемым этапом с резервным копированием; простой `wrangler deploy` их не применяет.
- Сборки веток/PR не должны подключаться к личной production-D1. Их адреса должны быть закрыты Access или отключены.

В репозитории сейчас нет настроенного автодеплоя. Push в GitHub означает сохранение исходников, а не публикацию Worker.

## Типичные проблемы

| Симптом | Что проверить |
| --- | --- |
| `503 AUTH_CONFIGURATION_ERROR` | Все три `ACCESS_*` заданы в нужном Worker; issuer имеет вид `https://team.cloudflareaccess.com`; после настройки выполнен деплой |
| `401 AUTH_REQUIRED` после входа | Совпадают issuer и AUD именно этого Access-приложения; Access передаёт подписанный assertion; сессия ещё действует |
| `403 ACCESS_DENIED` | Политику Access и точный email; для изменяющих API-запросов также нужны совпадающий Origin и JSON |
| `DB` отсутствует / `no such table` | Binding называется `DB`, указан верный UUID и миграции применены с `--remote` к нужной базе |
| Видна пустая история | Не подменён ли `database_id`; не выбрана ли другая дата/зона; локальная и удалённая базы различаются |
| `TIMEZONE_CHANGED` | Часовой пояс изменился; обновите настройки/страницу. Ручной ввод пока требует совпадения зоны устройства и приложения |
| Переменные пропали после деплоя | Если использовали Dashboard Variables, нужны `--keep-vars` / `keep_vars: true` либо те же значения в `vars` рабочего config |
| LLM не настроен / не работает | Наличие Secret, модель и доверенный base URL; лимиты/баланс поставщика. Учёт должен оставаться доступен |
| После `npm run dev` не работает API | Локальный Access login не реализован; один `.dev.vars` не создаёт подписанную сессию. Используйте тесты или отдельный защищённый тестовый Worker |
| Wrangler не может записать `~/.config` в облачной среде | В этой среде можно задать `XDG_CONFIG_HOME=/tmp/interruption-xdg` перед командой; это не нужно большинству локальных установок |
